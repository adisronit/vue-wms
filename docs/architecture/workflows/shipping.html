ShippingImplemented

Shipping represents outbound dispatch confirmation only — it has no inventory dependency at all, because Picking already removed the stock when it picked the lines this shipment covers.

Implementation Notes

  • Shipping has no inventory dependency, by design: the package is grepped and confirmed to import neither internal/inventory nor its Service type. Across Create, Confirm, and Cancel, no method in this package ever calls AddStock, RemoveStock, or MoveStock (package doc comment, model.go:1-16, service.go:1-14).
  • Create (POST /shipping, shipping.create) requires the linked picking task to be picking.StatusCompleted or picking.StatusShortPick, checked through a narrow pickingChecker interface backed by picking.Service.Get — not a direct dependency on Picking's full service (service.go:129-143).
  • Shippable lines are picking items with ItemStatusCompleted && PickedQty>0; none found returns ErrNoShippableItems before any database write happens (service.go:138-145).
  • One shipment per picking task is enforced twice: an application-level pre-check against FindByPickingTaskID, and a database UNIQUE constraint as the final backstop — either path returns ErrAlreadyShipped (service.go:160-164, 196-201).
  • Item quantities are copied verbatim from the picking task's PickedQty; CreateRequest has no client-supplied Items field at all, so "shipment qty ≤ picked qty" is enforced by construction, not a range check (service.go:129-134, 186-193).
  • Confirm (POST /shipping/{id}/confirm, shipping.approve) applies exactly one of DISPATCH / DELIVER / ISSUE per call, gated by CanDispatch/CanDeliver/CanReportIssue; no inventory mutation happens anywhere in Confirm — annotated explicitly in the source, since Picking already removed the stock (service.go:249-320, model.go:47-70).
  • Cancel (POST /shipping/{id}/cancel, shipping.update) is only allowed from READY, i.e. before dispatch, and never restores or mutates inventory — cancelling a shipment is not an un-pick; the stock stays removed (service.go:343-376, model.go:85-87).
  • Confirm's idempotency guard follows the same pattern as Picking/Receiving: insert into shipment_confirmations after confirming the shipment exists, so a duplicate key returns the current state instead of re-applying a transition (service.go:264-278, 324-329).
