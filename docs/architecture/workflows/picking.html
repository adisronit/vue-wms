PickingImplemented

Creating a picking task reserves stock immediately; only Confirm's PICKED lines actually remove it and write the inventory ledger. Cancel and SHORT lines only ever release a reservation that was never drawn down.

Implementation Notes

  • Create (POST /picking, gated by picking.create) validates warehouse existence, priority, ordered_qty>0, product existence, and that the location resolves, belongs to the same warehouse, and is ACTIVE — then reserves each line's full quantity via ReserveStockTx inside one transaction with the header insert; the header's status is always PENDING at creation (handler.go:211, service.go:111-239).
  • Reservation is a claim, not a movement: ReserveStockTx only ever touches reserved_quantity. It never touches quantity and never writes an inventory_transactions row (service.go:220-239).
  • Confirm (POST /picking/{id}/confirm, gated by picking.update — a lower bar than Cancel) processes one or more lines per call, each flagged PICKED or SHORT. PICKED calls ConsumeReservationTx, which atomically decrements the reservation and removes the real stock, writing the PICK ledger row in the same call. SHORT only calls ReleaseReservationTx for the unpicked remainder — it writes no ledger row at all (service.go:261-390).
  • The whole Confirm request is one transaction: any single line's error (insufficient stock, reservation underflow, an already-resolved line) rolls back every line in that call, including ones already processed earlier in the same call (service.go:296-390).
  • Confirm's idempotency guard inserts into picking_confirmations before checking CanConfirm(), deliberately, so a nonexistent task id raises a clean 404 instead of a raw FK-violation 500; a duplicate idempotency_key hits that table's PRIMARY KEY and is treated as a successful no-op, returning the task's current state rather than mutating stock a second time (service.go:280-294, 400-405).
  • Cancel (POST /picking/{id}/cancel) is gated on picking.approve — not picking.update — the one other picking.* permission code, deliberately set at a higher bar than Confirm's execution-level gate (handler.go:40-57, 288).
  • Cancel only ever releases whatever a still-open line's remaining (ordered − picked) quantity reserved; it never calls RemoveStockTx and never writes a ledger row. Lines already COMPLETED or SHORT are skipped by status, not by remaining quantity, since a SHORT line's remainder is not a reliable "still reserved" signal (service.go:419-495).
  • The header's status is derived, never stored imperatively: computeTaskStatus reads every line's terminal/non-terminal state to decide COMPLETED, SHORT_PICK, IN_PROGRESS, or PENDING (model.go:188-229).
