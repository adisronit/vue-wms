Stock CountImplemented

Counting a location freezes a live balance snapshot the moment a line is added, then offers two mutually exclusive ways to apply the resulting variance: Confirm applies it directly, or Create Adjustments defers it into separately-approved stock-adjustment documents.

Implementation Notes

  • Create (POST /stock-counts) and AddItem (POST /stock-counts/{id}/items, stock_adjustment.update) both reuse stock_adjustment.* permission codes — there are no distinct stock_count.* codes anywhere in this system, including for Confirm (handler.go:39-46).
  • Freeze is literal. Adding a line reads the LIVE balance via inventory.FindBalance at that exact instant and stores it as the item's SystemQty. Nothing in this package ever writes to that column again (service.go:245-268).
  • RecordCount (PUT /stock-counts/{id}/items/{itemId}) only runs while the count is DRAFT. It computes variance := countQty - item.SystemQty immediately and stores both values as a historical fact, well before Confirm ever runs (service.go:278-324).
  • The stale-balance check is a live-vs-frozen-snapshot comparison, not a version or timestamp column. Inventory balances carry no version field at all. Confirm re-reads the current live balance inside the same transaction and compares it against the item's frozen SystemQty for every counted line (service.go:398-418).
  • A mismatch returns ErrStaleCount → HTTP 409 STALE_COUNT_CONFLICT, rolling back the entire Confirm call, including lines whose variance was already applied earlier in that same call (service.go:417).
  • Confirm and Create Adjustments are mutually exclusive by construction, not by application-level checking alone. Both call the identical Repository.ClaimStatus — a guarded UPDATE ... WHERE status='DRAFT' — targeting different destination statuses (CONFIRMED vs. ADJUSTMENT_CREATED). Zero rows affected means the other path already won the race (service.go:373-374, 514-515).
  • Confirm applies nonzero variances directly via AddStockTx/RemoveStockTx, type COUNT, inside the claimed transaction (service.go:420-432).
  • Create Adjustments (POST /stock-counts/{id}/create-adjustments, stock_adjustment.create) instead generates one PENDING stockadjustment document per nonzero-variance line via CreateTx, in the same transaction as its own claim. Neither this method nor the documents it creates mutate inventory themselves — that only happens later, when a separate approver confirms each document through stockadjustment's own normal lifecycle (service.go:487-548).
