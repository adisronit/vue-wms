PutawayImplemented

Confirming a putaway task moves stock from a source location to a destination within one SQL Server transaction, enforcing a single zone-type placement rule and recording an issue flag per line when a line cannot be put away.

Implementation Notes

  • Trigger is POST /api/v1/putaway/{id}/confirm, gated by putaway.approve — the same segregation-of-duties pattern as Receiving: PUTAWAY staff can create tasks but not confirm the stock move (handler.go:25-39, 47).
  • A putaway task optionally links back to the receipt it came from via Task.ReceiptID; GET /putaway/sources/{receiptId} computes the remaining puttable quantity per line as received_qty - SUM(moved_qty) (model.go:103; repository.go:397-428).
  • Per-line confirmation branches on Action: an ISSUE line requires a non-empty remark, flags the item, and skips stock movement entirely — it does not touch inventory or fail the transaction (service.go:315-326).
  • The zone-type check is the entire placement rule. A CONFIRMED line's destination must be in the same warehouse, ACTIVE, and in a STORAGE-type zone. Known gap: there is no numeric capacity or volume check anywhere in putaway (service.go:340-352).
  • Lot number and expiry date are carried forward from the source balance row itself (via FindBalance), not from user input — so "lot identity matches source" and "expiry unchanged" hold by construction, not by a separate check (service.go:361-367).
  • MoveStockTx runs inside the same open transaction and is internally composed as a removeStockTx-at-source leg plus an addStockTx-at-destination leg sharing one reference_id — two ledger rows, one all-or-nothing unit (service.go:369-379).
  • moved_qty is updated via a guarded atomic UPDATE (AdjustMovedQty), the same lost-update-race fix pattern applied to Receiving's AdjustReceivedQty (repository.go:301-321).
  • ErrInsufficientStock/ErrNoStock from the inventory core are translated into a validation error at the putaway layer, and the whole transaction rolls back (service.go:375-378).
