Reservation & CancellationImplemented

There is no dedicated Reservation module, service, or table anywhere in the codebase. Reservation is a single column plus three guarded functions inside Inventory Core, consumed by Picking and Replenishment; Order, Receiving, Putaway, and Shipping cancel without ever touching a reservation because none of them ever created one.

Implementation Notes

  • Reservation lives entirely inside internal/inventory (Inventory Core) as the inventory.reserved_quantity column. Available() is derived as Quantity - ReservedQuantity and is never itself stored, so it can never drift out of sync.
  • The entire mechanism is one guarded SQL statement, AdjustReservation, wrapped by three service functions: ReserveStockTx (positive delta, claims stock), ReleaseReservationTx (negative delta, frees a claim without moving stock), and ConsumeReservationTx (release paired 1:1 with a real stock deduction at confirm time).
  • None of the three functions write a row to inventory_transactions. A reservation is a claim against an existing balance, never a movement of it — this is stated explicitly in the source comments and is the reason reservation and the movement ledger are two independent concerns.
  • Picking reserves the full ordered quantity at task creation, releases the short/unpicked remainder and consumes the picked portion at confirm, and releases whatever remains on any still-open line at cancel.
  • Picking's Cancel is only reachable while the task is PENDING or IN_PROGRESS — the CanCancel() status guard runs before any reservation line is touched, which is what makes a retried or duplicate cancel call safe (it is rejected before it can double-release).
  • Replenishment follows the identical reserve-at-create pattern, releasing on either Cancel or ReportIssue — two different trigger points that both call the same ReleaseReservationTx.
  • Order's own Cancel deliberately never calls ReleaseReservationTx and never touches inventory at all, because Order itself never reserves anything — reservation ownership belongs entirely to Picking once a picking task exists for the order. Order's cancel is only permitted while the order is still PENDING (pre-picking).
  • Receiving, Putaway, and Shipping all expose a Cancel endpoint, but each is confirmed by source inspection to involve zero reservation or stock-movement calls: Receiving's cancellable state by definition has no stock movement to undo, Putaway never reserves at task-creation time and rejects cancellation once any line has already moved stock, and Shipping's cancel has no inventory dependency at all.
