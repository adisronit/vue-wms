AuthenticationImplemented

Login verifies credentials with bcrypt and issues an HS256 JWT that embeds the user's role and permission codes; every protected route then authorizes purely from that token, without a per-request database lookup.

Implementation Notes

  • Login is fully synchronous: a sequence of independent reads plus one best-effort write, with no multi-statement atomicity requirement, so no SQL transaction and no RabbitMQ are involved (service.go:61-105).
  • ErrInvalidCredentials is deliberately identical for "no such user" and "wrong password" to prevent username enumeration via the login endpoint (service.go:15-18, 63-65, 70).
  • Account status is checked only after credentials verify, so an inactive/locked account gets its own distinct error (ErrAccountNotActive, 403) once identity is already confirmed (service.go:74-76).
  • UpdateLastLogin runs after the token is issued and is best-effort: a failure is logged but never turns a successful login into an error response (service.go:88-96).
  • Known tradeoff / gap: permissions are embedded directly in the JWT at login time rather than re-queried from SQL Server on every request. A role or permission change for a logged-in user only takes effect the next time that user logs in again — there is no per-request database re-check (permission.go:18-23).
  • Every protected route chains RequireJWT (validates HS256 signature + expiry) then RequirePermission (string-matches the requested code against the JWT's embedded permissions claim) before reaching the handler.
