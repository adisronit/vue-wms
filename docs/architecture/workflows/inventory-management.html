Inventory ManagementImplemented

This is not an HTTP-triggered workflow but the shared core library every other inventory-moving workflow calls into: a small set of guarded-UPDATE primitives for balance writes and reservation claims, always composed inside the caller's own open transaction.

Implementation Notes

  • There is deliberately no direct route into this module's mutations. Handler only wires List/Get/Summary/Transactions/Export (read-only); AddStock/RemoveStock/MoveStock are never reachable from HTTP (handler.go:16-25).
  • AddStockTx/addStockTx performs one guarded UPDATE (AdjustBalance); if it affects 0 rows because the balance row doesn't exist yet, it inserts a new balance row, then always inserts one inventory_transactions ledger row (service.go:186-191, 417-452).
  • RemoveStockTx/removeStockTx uses the same guarded UPDATE with a negative delta; a 0-row result is disambiguated with a follow-up read into ErrNoStock (row absent) vs ErrInsufficientStock (row exists, insufficient) (service.go:198-233, 454-490).
  • MoveStockTx/moveStockTx is composed as removeStockTx-at-source plus addStockTx-at-destination sharing one reference_id, both inside one transaction (service.go:239-268, 382-415).
  • Reservation primitives — ReserveStockTx, ReleaseReservationTx, ConsumeReservationTx — only ever claim against the balance's reserved_quantity column: they never write a ledger row and never touch quantity directly. ConsumeReservationTx composes a release with removeStockTx, which does write a PICK-type ledger row (service.go:280-299, 305-320, 333-348).
  • Known gap / explicit design choice: the guarded single-statement UPDATEs (AdjustBalance, AdjustReservation) are the sole concurrency control in this module. There are no explicit row locks (SELECT ... FOR UPDATE / WITH (UPDLOCK)) and no optimistic-version column anywhere. DB CHECK constraints (CK_inventory_quantity_non_negative, CK_inventory_reserved_within_quantity) are the backstop (repository.go:303-333; migrations/0009:50-51).
  • Eight transaction types are enforced by a CHECK constraint: RECEIVE, PUTAWAY, MOVE, PICK, SHIP, ADJUST, RETURN, COUNT (migrations/0010:43-44).
  • Every real caller composes through the *Tx variants, constructing inventory.NewRepository(tx) bound to its own already-open *gorm.DB — never the self-transacting non-Tx variants. Receiving calls AddStockTx; Putaway calls MoveStockTx; Picking calls Reserve/Release/ConsumeReservationTx; Replenishment calls Reserve/Release/MoveStockTx; Stock Adjustment and Stock Count both call AddStockTx/RemoveStockTx.
