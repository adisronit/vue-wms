ReceivingImplemented

Confirming a receipt validates each line against business rules, then writes inventory and the receipt's own received quantities inside one SQL Server transaction guarded by an idempotency key, so retried or duplicate confirmations are handled safely.

Implementation Notes

  • Trigger is POST /api/v1/receipts/{id}/confirm, gated by the receiving.approve permission — a deliberately higher bar than receiving.create/receiving.update, so RECEIVING staff can build and edit receipts but not confirm the stock movement itself (handler.go:26-34, 51).
  • The HTTP request context is detached (dbctx.Detach) before the transaction opens, specifically to avoid orphaning the transaction if the client disconnects mid-request — a real bug found and fixed in an earlier phase (service.go:322-328).
  • Receipt existence is checked before the idempotency-key insert, deliberately, to avoid a raw FK-violation 500 in place of a clean 404 (service.go:332-345).
  • A duplicate idempotency key is not treated as an error: the insert fails on its UNIQUE constraint, and the service returns the current (already-correct) receipt state as an idempotent no-op (service.go:347-350, 449-454).
  • AddStockTx is called inside the same open transaction as the receipt-line updates, via an inventory.Repository bound to the same *gorm.DB — not a second, disconnected transaction (service.go:358, 410-416).
  • received_qty is updated with a guarded atomic UPDATE (AdjustReceivedQty), replacing an earlier read-modify-write that had a lost-update race under concurrent confirms (repository.go:323-330).
  • Any error anywhere in the transaction closure — a validation failure, a product/location lookup failure, an inventory-write failure — rolls back the whole transaction, including lines already processed earlier in the same call (service.go:312-316).
  • Known gap: there is no purchase-order entity in this system. expected_qty is simply user-entered when the receipt is created; it is never validated against an external PO.
