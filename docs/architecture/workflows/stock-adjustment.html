Stock AdjustmentImplemented

A stock adjustment is a controlled correction document. Create and Update never touch inventory regardless of status — only Confirm's APPROVE action does, and a background reminder scanner nudges approvers about documents left pending too long.

Implementation Notes

  • Only Approve ever mutates inventory. Create (POST /stock-adjustments, stock_adjustment.create) never calls AddStockTx/RemoveStockTx regardless of whether the client creates the document as DRAFT or PENDING — it is a controlled correction document, not a movement in itself (service.go:115-161).
  • Create's before_qty snapshot is display-only: it is read from the live balance at creation time purely for the UI, and is never used to compute the Confirm-time mutation (service.go:134-139).
  • Update (PUT /stock-adjustments/{id}, stock_adjustment.update) is only allowed while the document is DRAFT (CanEdit()) — PENDING documents are frozen for editing (service.go:220-232, model.go:37-41).
  • Confirm (POST /stock-adjustments/{id}/confirm, stock_adjustment.approve) is gated to PENDING only via CanConfirm(), with the usual idempotency guard inserted before that gate check (service.go:289-318).
  • APPROVE calls inventory.AddStockTx (increase) or RemoveStockTx (decrease) inside the same transaction as the status update — the one and only point in this package's entire lifecycle where inventory.quantity ever changes. AfterQty is populated from the mutation's returned balance, never from client input (service.go:328-364).
  • REJECT makes zero inventory.* calls. It only requires a remark and sets status to REJECTED — there is no separate Cancel endpoint for this package; REJECT is the only non-approve terminal transition (service.go:366-376).
  • The reminder pipeline is a separate, non-critical, asynchronous side-process: a server-owned ticker (not the HTTP handler) scans for overdue PENDING adjustments past a cooldown, using a claim-based read (ClaimAndListOverdueForReminder) specifically to prevent duplicate publishes under concurrent ticks (main.go:346-371).
  • The Worker ACKs a reminder delivery only after NotifyStockAdjustmentReminder succeeds, which resolves every ACTIVE user holding stock_adjustment.approve and inserts one notification row per recipient, unique on (message_id, user_id) for idempotent redelivery (worker/main.go:195-210).
