Request PipelineImplemented

Every request to /api/v1/* passes through engine-level middleware, a two-stage JWT + permission gate, and into one of 20 business modules; a small number of named exceptions bypass part of that gate, and exactly one endpoint runs asynchronously through RabbitMQ instead of returning a result directly.

Implementation Notes

  • Engine-level middleware — Recovery, RequestID, RequestLogging, CORS — is wired via engine.Use(...) and must run before engine.Group("/api/v1") creates the route group, because Gin copies the parent's current middleware chain at the moment Group() is called.
  • This ordering was a real, previously-undetected bug: middleware added via a bare engine.Use() call after the group already existed never actually ran for any /api/v1/* route. It was discovered when request_id showed up empty in every transaction log. Most seriously, Recovery() not running meant an unrecovered panic in any handler could have crashed the entire process for every in-flight request.
  • Every protected route passes through two stages in order: RequireJWT(secret) validates the Bearer HS256 token and returns 401 on failure, then RequirePermission(code) string-matches the JWT's embedded permissions claim array and returns 403 on failure.
  • Three named exceptions to the two-stage gate: GET /health has no auth at all; POST /auth/login is public (it is what issues the JWT in the first place); GET /auth/me only requires RequireJWT, with no RequirePermission check.
  • All other routes — 20 business modules in total — sit behind both stages and follow the standard Handler → Service → Repository → SQL Server layering.
  • Exactly one endpoint is asynchronous: POST /reports/inventory-transactions/export creates a PENDING row in export_jobs, publishes a message to the RabbitMQ queue wms.report.export, and returns 202 Accepted immediately. The caller polls GET /reports/export-jobs/{id} for status and downloads the result once COMPLETED.
  • This is easy to confuse with the CSV "Export" endpoints that exist on inventory, receiving, putaway, picking, shipping, stockadjustment, and stockcount — those are all synchronous streamed file downloads. They are not jobs, they do not touch export_jobs, and they never involve RabbitMQ.
  • Swagger UI is mounted directly on the raw Gin engine at /swagger/*any, conditionally on cfg.SwaggerEnabled — it sits outside the /api/v1 route group entirely, so it is unaffected by the group's auth middleware. It is reachable at http://localhost:8080/swagger/index.html.
  • Every protected handler's swaggo annotation block declares @Security BearerAuth, matching its actual middleware wiring — verified by sampling handlers across modules rather than assumed.
