Implementation Notes

  • Migration-verified — all 6 tables trace to real CREATE TABLE/ALTER TABLE statements in backend/migrations/0011–0016 and 0032; no model-only tables exist in this schema.
  • No PO cross-validation: receipts.vendor is a plain string, not a foreign key to a supplier/purchase-order entity — no such entity exists anywhere in this codebase, so there is nothing to validate a receipt's vendor or expected quantities against.
  • receipt_items has no CHECK(received_qty <= expected_qty) — over-receipt is a deliberately supported business case, not a rejected one; the create form's own variance display colors a positive variance green rather than flagging it as an error.
  • No location capacity check: no numeric location capacity/volume constraint exists anywhere in this schema — only zone-type classification (RECEIVING/STORAGE/PICKING/...) constrains where stock can sit, not how much.
  • putaway_tasks.receipt_id is a nullable FK to receipts — the normal path pre-loads items from a completed receipt, but the same screen also supports ad-hoc putaway with no source document at all; putaway_task_items.receipt_item_id is nullable for the same reason, line by line.
  • putaway_task_items carries two separate FK roles into locations — source_location_id and destination_location_id — both shown as distinct relationships on the diagram.
  • Every *_confirmations table here (receipt_confirmations, putaway_confirmations) is a pure idempotency guard: PK is the client-generated idempotency_key, with one FK back to its own header table — not a classic parent-child relationship.
