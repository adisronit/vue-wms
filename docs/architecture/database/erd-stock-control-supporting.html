Implementation Notes

  • Migration-verified — all 11 tables trace to real CREATE TABLE/ALTER TABLE statements in backend/migrations/0023–0028, 0030, 0031, and 0033–0037; no model-only tables exist in this schema.
  • The confirmations pattern: every *_confirmations table across the whole schema (receipt/putaway/picking/shipment/stock_adjustment/stock_count/replenishment_confirmations) shares the identical shape — idempotency_key as PK, one FK back to its own header table. It is a "one guard row per confirm click" idempotency pattern, not classic parent-child cardinality; a row existing only proves that a specific client-generated key has already been processed once.
  • stock_adjustment_items.before_qty/after_qty are display snapshots only, captured for the UI's "Current Qty"/"New Qty" columns — adjust_qty is the sole authoritative delta, applied via AddStockTx/RemoveStockTx's own atomic guarded UPDATE against whatever the live balance actually is at approval time.
  • stock_count_items.system_qty is captured once, when the line is added to the count, and is never refreshed afterward — a deliberately frozen historical snapshot, unlike inventory's own live balance.
  • stock_counts.source_stock_count_id lives on stock_adjustments (added by migration 0031) as a nullable FK — one stock count can generate multiple adjustment documents (one per non-zero-variance line), so this is a plain one-to-many FK on the "many" side, not a join table.
  • notifications and export_jobs only have a foreign key to users (recipient / requester respectively) — they have no relationship to any other table in this schema, including the stock adjustment they may be about (that link is carried as a loosely-typed reference_type/reference_id pair, not a real FK).
  • stock_adjustment_reminders.stock_adjustment_id doubles as both the primary key and the uniqueness guard — at most one reminder-tracking row per adjustment, enforced by the PK itself rather than a separate UNIQUE constraint.
