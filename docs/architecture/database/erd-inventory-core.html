Inventory CoreMigration-Verified

Full column/PK/FK detail for the 2 tables at the center of the schema: inventory (the current on-hand balance per product/location/lot) and inventory_transactions (the append-only movement ledger every other domain writes through). products, locations, and users appear here only as external reference nodes — see the Identity & Warehouse ERD for their full detail.

Implementation Notes

  • Migration-verified — both tables trace to real CREATE TABLE statements in backend/migrations/0009 and 0010; no model-only tables exist in this schema.
  • No explicit row-locking or optimistic-version column exists on inventory. Concurrency safety relies entirely on single-statement guarded UPDATEs — AdjustBalance/AdjustReservation in internal/inventory/repository.go — plus the table's own CHECK constraints as a database-level backstop, not application-level locking.
  • inventory.lot_no is VARCHAR(50) NOT NULL DEFAULT '', deliberately not nullable: a nullable lot_no would let SQL Server's unique-index NULL semantics silently allow duplicate "no-lot" balance rows for the same product+location instead of merging into one row (the same lesson learned the hard way with products.barcode in migration 0008).
  • inventory_transactions.reference_type / reference_id are loosely-typed strings, deliberately not foreign keys — they point at whatever document a workflow uses (a receiving number, an adjustment number, ...) without taking a schema dependency on those workflow tables.
  • inventory_transactions is append-only by design: no updated_at column and no UPDATE/DELETE code path anywhere in the codebase.
  • inventory's own CHECK constraints enforce quantity >= 0 and 0 <= reserved_quantity <= quantity as a hard backstop, independent of whatever the application layer does.
