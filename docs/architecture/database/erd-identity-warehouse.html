Implementation Notes

  • Migration-verified — all 9 tables trace to real CREATE TABLE/ALTER TABLE statements in backend/migrations/0001–0040; no model-only tables exist in this schema.
  • products.barcode uses a filtered UNIQUE INDEX ... WHERE barcode IS NOT NULL rather than a plain UNIQUE constraint, because SQL Server treats every NULL as distinct under a plain unique constraint — a plain constraint would still allow duplicate non-null barcodes to slip through once a NULL row exists, so the filtered index is the deliberate workaround.
  • products.default_zone is a plain VARCHAR, not a foreign key to zones(id) — the frontend's zone picker has no warehouse context, so it cannot be resolved to a real zones row without inventing a relationship the UI doesn't establish.
  • users.warehouse_id (nullable, FK → warehouses) and users.last_login_at were both added later by migration 0039 — no warehouse-scoped authorization logic exists anywhere in the codebase yet, so NULL simply means "not assigned to a specific warehouse."
  • role_warehouse_access (migration 0040) is the newest table in this domain, added to back the Role & Permission screen's previously mock-only "Warehouse Access" panel. Its role_id FK cascades on delete (matching role_permissions); its warehouse_id FK does not.
  • role_permissions and role_warehouse_access are both pure composite-primary-key join tables with no surrogate id column.
  • zones.type is CHECK-constrained to 7 values (RECEIVING/STORAGE/PICKING/PACKING/SHIPPING/QC/HOLD); zones also carries UNIQUE(warehouse_id, code) and locations carries UNIQUE(zone_id, code).
