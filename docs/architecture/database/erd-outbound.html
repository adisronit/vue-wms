Implementation Notes

  • Migration-verified — all 8 tables trace to real CREATE TABLE/ALTER TABLE statements in backend/migrations/0017–0022, 0029, 0032, and 0038; no model-only tables exist in this schema.
  • picking_tasks is the fulfillment hub: shipments.picking_task_id is a required UNIQUE FK — exactly one shipment per picking task, no partial shipment supported — and orders.picking_task_id is a nullable UNIQUE FK, at most one order per picking task. Both FKs live on the other table, pointing back at picking_tasks.id.
  • picking_tasks.order_no is plain text, not a foreign key — the Order Management module (orders/order_items, migration 0038) did not exist when picking_tasks was first created, so no Sales Order entity was available to reference. customer is plain text for the same reason.
  • picking_task_items.location_id is the source location only — picking never has a destination the way putaway does, since Confirm only ever removes stock.
  • shipment_items.qty is copied from the linked picking_task_items.picked_qty at shipment-creation time and never independently edited afterward — there is no per-line quantity input anywhere in the Shipping UI.
  • shipment_items.location_id and picking_task_item_id exist purely for traceability — Shipping performs no inventory mutation of its own (no AddStock/RemoveStock/MoveStock call anywhere in internal/shipping).
  • order_items carries no location or lot column — Order Management is deliberately location-agnostic, the same way a real sales order would be; Picking is where a location/lot actually gets chosen.
  • orders.external_reference is a nullable UNIQUE column reserved as a future ERP idempotency key, not yet populated by any current workflow.
