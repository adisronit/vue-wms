Live NARM/WMS is untouched and will remain untouched until a separate, explicit approval.

## Scope correction from the original Phase 5 draft

The original Phase 5 ask (generic demo tenant) has been superseded by the clarification: **demo data goes into the existing EWTA tenant (id=2)**, reusing the real warehouse (EWTA-WH, id=7) and all 39 products, not a separate synthetic tenant. Isolation is by **naming convention**, not by tenant boundary: every new record this generator creates carries a `DEMO-EWTA-20261118` reference/code, so it's trivially identifiable and selectively removable without touching real EWTA records.

## Reference/code convention (the isolation mechanism)

Every natural-key field this tool writes gets a `DEMO-EWTA-20261118-####` value: receiving doc numbers, order numbers, stock count reference, adjustment reference, relocation reference, replenishment reference, picking batch reference, packing job number, loading trip number, transfer reference. Rows with no natural-key field of their own (inventory_transactions ledger rows, picking_task_items, carton_contents, etc.) are identified by FK linkage to a parent row that does carry the prefix — documented per table in the implementation, not guessed at runtime.

A companion **manifest file** (JSON, written outside the DB — e.g. `docs/demo-data/EWTA-DEMO-20261118-manifest.json`, kept separate from the real `docs/demo-data/EWTA/` customer-onboarding files already in this repo) records every row created: table name, primary key, and reference code. This is both the idempotency check (re-running the tool looks up each natural key before inserting, skips if found) and the exact input to a selective cleanup script (`DELETE ... WHERE id IN (...)` per table, FK-ordered, never a blanket `DELETE`/`TRUNCATE`).

## Why service calls, not raw INSERTs

Every stage below calls the same `internal/<module>.Service` methods the real handlers call (e.g. `receiving.Service.Create`/`Confirm`, `picking.Service.Confirm`, `inventory` is never touched directly — it's a side effect of Putaway/Picking/Relocation/etc. going through their own services). This is required by the brief ("use existing application services/workflows... rather than inserting arbitrary rows that bypass business rules") and also means the generator exercises the same validation, RBAC checks, and stock-engine invariants (reserved+hold<=quantity, no negative stock) as real usage — if the generator can create a scenario, production can too.

## Stage plan, flows, and target counts

| Stage | What it does | Target count |
|---|---|---|
| Warehouse Layout | `warehouselayout.Service` — one version + rack/level/location objects for EWTA-WH, positioned to match the 8 existing zones | 1 version, ~80-100 placed objects (mix of occupied/empty once inventory exists) |
| Receiving | `receiving.Service.Create`+`Confirm` against existing suppliers/products | 10 receiving docs, 2-4 lines each |
| QC | `qualitycheck.Service` — mix of outcomes per line | ~60% PASS, ~25% HOLD (later released), ~15% REJECT |
| Putaway | `putaway.Service` for every PASSed/released line | Completes for all PASS lines; 1-2 left pending to show in-progress state |
| Stock Count | `stockcount.Service` — count a subset of locations, deliberate variance on 2-3 lines | 2 counts |
| Stock Adjustment | `stockadjustment.Service` approving the count variances | 1 adjustment batch |
| Relocation | `relocation.Service` moving stock between existing locations | 3 relocations |
| Replenishment | `replenishment.Service` bulk→pick-face | 2 tasks |
| Orders | `order.Service.Create`, varied `order_type` | 12 orders across the full status spread (PENDING→DISPATCHED), including 1-2 deliberate short-pick/insufficient-stock cases |
| Picking | `picking.Service` batches + confirmations, incl. a structured short-pick | 3 batches covering the 12 orders |
| Packing | `packing.Service` cartons for picked orders | 4-6 packing jobs |
| Loading | `loading.Service` trips bundling shipments | 2 trips |
| Shipping | dispatch via `shipping.Service`, 1 trip left loaded-not-dispatched | 8 dispatched, 1 in-progress |
| Transfer (if approved) | Order with `order_type=INTERNAL_TRANSFER` → pick → in-transit virtual location → destination `transferreceipt.Service` confirm | 2 transfers, 1 left in-transit |
| Reports/KPI | No separate writes — derived from the above. Acceptance = every report (Receiving, Stock Count, Picking Issue, Inventory, Picking KPI, QC, Delivery) returns non-empty, internally-consistent rows for the demo date range and reconciles against the operational rows created | — |

Stock lifecycle followed exactly as documented in `docs/proposals/wms-phase33-outbound/00-checkpoint.md` (Putaway is where stock first lands via `AddStockTx`; Picking.Confirm is where it actually leaves via `ConsumeReservationTx`; Shipping never touches inventory directly) — the generator relies on this, it doesn't reimplement stock math.

## Acceptance criteria (cross-cutting)

- Re-running the generator against the same database produces **zero** additional rows (every natural key already exists → skip).
- Zero orphaned records — every FK the generator writes resolves to a real row (either pre-existing EWTA master data or a row the generator itself created earlier in the same run).
- Zero negative inventory; `reserved_quantity + hold_quantity <= quantity` on every balance row, at every point, not just at the end.
- Zero cross-tenant writes — every row's `tenant_id = 2`, verified by a post-run query, not assumed.
- Every status value the generator leaves behind was reached by calling the real service transition, never hand-set.
- The 7 reports + Warehouse 2D Layout all render non-empty, internally consistent data against what was generated.
- Full manifest produced, and a dry-run/preview mode exists that reports exactly what *would* be created without writing anything.

## Implementation plan

New `backend/cmd/demodata/main.go`, same shape as `cmd/migrate`: subcommands `preview` (dry run, no writes) and `run` (idempotent, writes + manifest). Refuses to run at all if `DB_NAME` doesn't match an explicit `--confirm-target=<name>` flag the operator must pass — a deliberate extra guard against ever pointing this at the wrong database by a copy-paste env var mistake.
