# Phase 29A — Tenant Database Isolation: Implementation Notes

**Status:** Implemented and tested against disposable SQL Server instances. Not applied to any real/shared environment. Branch `feat/wms-29a-database`, building on the Phase 28 commit `5fc523a` (`feat(wms): phase28 add multi-tenant database foundation`).

**Scope boundary, stated explicitly:** this phase owns SQL migrations, tenant-related GORM model changes, and migration tests only. Auth (`internal/auth`), API handlers, and `docs/architecture/` were not touched. No repository, service, or handler code was modified — every existing code path that creates a business row continues to run completely unmodified; the database-level `DEFAULT` constraints added here (§3) are what make that safe. Threading real tenant context through the application layer is Phase 29B+, per `saas-module-roadmap.md`.

## 1. Step 1 — Verification Findings and Corrections

Before writing any SQL, `tenant-er-design.md` and `migration-plan.md` were re-read against each other and against the real, already-applied migrations `0001`–`0042`. Four concrete discrepancies were found and resolved — the same kind of cross-document reconciliation `phase28-implementation-notes.md` §1 performed for its own phase:

- **`role_permissions`/`role_warehouse_access` tenant_id column.** `migration-plan.md` §2's file list for `0043a` includes both tables; `tenant-er-design.md` §3's own reclassification table explicitly marks both "Inherited, no own column needed" (tenant scoping flows through `role_id` once `roles.tenant_id` exists). Resolved in favor of the ER design: neither table gained its own `tenant_id` column. A redundant column here would need its own consistency enforcement (trigger or app-layer check) against `roles.tenant_id` for zero query-time benefit, since nothing joins through these two tables without already holding `role_id`.
- **Three missing document-number uniqueness corrections.** `tenant-er-design.md` §3's reclassification table lists `receipts.receipt_no`, `putaway_tasks.putaway_no`, `picking_tasks.pick_no`, `shipments.shipment_no`, and `orders.order_no`/`external_reference` as needing the `UNIQUE(code)` → `UNIQUE(tenant_id, code)` treatment, but omits `stock_adjustments.adjustment_no`, `stock_counts.count_no`, and `replenishment_tasks.task_no` (shown as "—" in that table's Old/New Unique Constraint columns) despite all three carrying the exact same globally-unique-human-readable-document-number pattern, confirmed by direct inspection of `migrations/0023`, `0026`, `0036`. Left unscoped, two tenants both generating, say, `ADJ-001` would collide. All three are rescoped in `0048` alongside the five the ER design did flag.
- **Migration ordering: SQL Server rejects `ALTER COLUMN` on a column a `UNIQUE` constraint already depends on.** `migration-plan.md` §2's own draft order is `0045` (tenant-scope unique constraints) before `0046` (`NOT NULL` + FK). Verified directly against a disposable SQL Server 2022 container: running the unique-constraint swap first, then attempting `ALTER TABLE roles ALTER COLUMN tenant_id BIGINT NOT NULL` fails with `Msg 5074: The object 'UQ_roles_tenant_code' is dependent on column 'tenant_id'` / `Msg 4922`, even for a nullability-only change with no type change. This phase's migrations run the reverse order — `0047` (`NOT NULL`/FK/indexes) before `0048` (unique-constraint swap) — which applies cleanly. See `0047`'s and `0048`'s own header comments for the full writeup at the point a future reader would hit it.
- **Migration version numbers must be purely numeric.** `cmd/migrate/main.go`'s `versionPattern = regexp.MustCompile(`^(\d+)_`)` matches a leading digit run immediately followed by `_` — a filename like `0043a_...` would silently fail to match and the migrate tool would skip the file entirely with no error. Discovered by reading the tool's own parsing code before naming any file, per this project's "do not guess requirements that can be discovered from source code" instruction, rather than following `migration-plan.md`'s own `0043a`/`0043b`/`0043c` lettered-suffix example literally. This phase's migrations are `0043`–`0048`, six purely-numeric versions, where the draft's lettered scheme would have needed four.

**Git/working-tree state confirmed before any file was written:** branch `feat/wms-29a-database`, clean, with the Phase 28 commit already present.

## 3. The `DEFAULT (1)` Safety Net — Why This Phase Needed One

`migration-plan.md` §3f's own draft leaves `tenant_id` with no default after the `NOT NULL`/FK step. That is fine if the very next phase also updates every repository/service call site to supply a real `tenant_id` on every insert. This phase does not do that — it is explicitly scoped to migrations, models, and migration tests only (see the top of this document). Every existing, unmodified `repository.Create(&Warehouse{...})`-shaped call in this codebase constructs its struct without ever setting `TenantID`, so without a default, the moment `0047` makes the column `NOT NULL` with an FK, GORM would send `tenant_id = 0` on the next insert and the FK would reject it outright — silently breaking every write path in the running application, with zero application-code change to blame it on.

`0047` instead sets every `tenant_id` column's `DEFAULT` to the literal value `1`, and every corresponding Go struct tag adds `default:1` — GORM's documented behavior is to omit a zero-value field from the generated `INSERT` when the field's schema has a configured default, letting the database supply it. Verified directly: `go run ./cmd/migrate seed`'s raw-SQL role inserts (which also never mention `tenant_id`) land on `tenant_id = 1` through the column default alone, with no Go-side involvement at all — proving the net also protects non-GORM callers, not just GORM ones.

**This only works if the bootstrap tenant is reliably `id = 1`.** `tenants.id` is `BIGINT IDENTITY(1,1)`, and SQL Server does not reuse a deleted identity value. During this phase's own iterative testing — rolling `0046` down and back up more than once while developing the migration — the bootstrap tenant's id drifted to `2`, then `3`, on successive re-applications, which would have silently orphaned every `DEFAULT (1)` constraint's FK reference. `0046`'s up-migration now wraps its tenant insert in `SET IDENTITY_INSERT tenants ON` / `OFF` to force `id = 1` explicitly, verified stable across two full down/up cycles in this session. In a real, one-time production application (`tenants` has never had a row before `0046` runs), this would have been true anyway without the explicit forcing — but forcing it costs nothing and makes the migration safe to roll back and reapply during further development, not merely safe to apply once.

## 5. Remaining Risks / Deferred to Phase 29B+

- **No application-layer tenant scoping exists yet.** Every IDOR/cross-tenant risk catalogued in `phase27-audit-report.md` is still fully present in the running application — this phase adds the `tenant_id` columns and database-level constraints, it does not add a single `WHERE tenant_id = ?` to any repository query, nor any tenant-extraction middleware. That is explicitly out of this phase's scope (see the top of this document) and remains Phase 29B+'s job.
- **`tenant_users` enrollment is a one-time, point-in-time backfill, not an ongoing process.** `0046` enrolls whichever `users` rows exist at the moment it runs. Any user created afterward by unmodified seed/signup code gets no `tenant_users` row automatically — confirmed directly in this session (seeding a fresh admin *after* `0043`-`0048` had already run produced zero `tenant_users` rows for them, which is why §4's verification deliberately seeded *before* applying this phase's migrations instead). Provisioning new users into `tenant_users` is application-layer work, not something a schema migration can or should own.
- **Per-tenant role-copy provisioning is still not implemented** — `phase28-implementation-notes.md` §6 already deferred this to Phase 29+; it remains deferred. `roles.tenant_id` now exists and is enforced, but nothing yet creates a second tenant's own copy of the RBAC catalog.
- **`RequirePlatformAdmin` middleware and any tenant-context middleware still do not exist.** Unchanged from Phase 28's own deferral.
- **Tests were run against disposable containers, twice, this session, by hand** — not wired into any CI/Docker Compose test target, consistent with Phase 28's own scope boundary.
